## 二、逐风险详细分析

### ✅ 风险一：LangChain —— 已确定不使用

**决策：使用 ChromaDB + DeepSeek 原生 API，零框架。**

LangChain 被排除的原因：
- 版本迭代太快（2024 年发了 3 个大版本），网上教程大量过期
- 抽象层太多，报错信息对新手不友好
- ChromaDB 的原生 API 只需要一行 `collection.query()`，不需要框架包装
- DeepSeek API 遵守 OpenAI 格式，`client.chat.completions.create()` 也是一行

**论文加分写法**："本系统采用轻量化原生实现方案，直接调用 ChromaDB 与 DeepSeek 原生 API，避免了 RAG 框架的抽象层开销与版本兼容风险，使得核心链路代码量控制在 50 行以内。"

---

### ✅ 风险二：FastAPI + Streamlit —— 保留但可控

**决策：保留双服务架构（Streamlit 前端 + FastAPI 后端）。**

保留的理由：
1. 你写过 JavaWeb（JSP + Controller），前后端分离的架构你**已经熟悉**
2. FastAPI 代码量很少（~30 行），但给论文提供了"API 接口设计"一整节内容
3. FastAPI 自带 Swagger `/docs` 页面，可以直接在网页上调试 API，**比 Streamlit 还方便调试**
4. CORS 只要一行 `allow_origins=["*"]`，不需要深入理解

**实际开发顺序**：先写 FastAPI + `/docs` 调试 RAG 逻辑 → 逻辑跑通后再加 Streamlit 壳。这样调试时根本不用打开 Streamlit，直接在 Swagger 页面里输入文本看 API 返回什么。

### 🔴 风险三：LLM 输出格式不稳定 —— 解析会出大问题

#### 风险描述

原方案设计 LLM 输出 JSON，但实际中 LLM 的输出**不可靠**：

```
你期望的输出：
{"is_ad": true, "risk_level": "高", ...}

你实际可能收到的：
```

```json
{"is_ad": true, "risk_level": "高", ...}
```

```json
{
  "is_ad": true,
  "risk_level": "高",
  ...
}
根据以上分析，该文本包含隐性广告。
```

```json
好的，我判断结果是：
{
  "is_ad": true,
  "risk_level": "高"
}
```

```json
（直接返回中文，根本没 JSON）
该文本明确包含隐性广告，风险等级为高风险...
```

```
**4 种异常情况，json.loads() 都会直接崩溃。** 如果你做 200 条测试 × 4 组实验 = 800 次调用，即使只有 15% 的异常率，也会有 120 次解析失败。手动重试不可接受。
```

#### 解决方案：多层容错解析策略

```python
import json
import re

def safe_parse_json(llm_output: str) -> dict:
    """多层容错解析，确保能从 LLM 输出中提取 JSON"""

    # 策略 1：直接解析（最理想情况）
    try:
        return json.loads(llm_output)
    except json.JSONDecodeError:
        pass

    # 策略 2：提取 ```json ... ``` 代码块
    match = re.search(r'```json\s*(.*?)\s*```', llm_output, re.DOTALL)
    if match:
        try:
            return json.loads(match.group(1))
        except json.JSONDecodeError:
            pass

    # 策略 3：提取 ``` ... ``` 任意代码块
    match = re.search(r'```\s*(.*?)\s*```', llm_output, re.DOTALL)
    if match:
        try:
            return json.loads(match.group(1))
        except json.JSONDecodeError:
            pass

    # 策略 4：正则匹配 JSON 对象 { ... }
    match = re.search(r'\{[^{}]*\}', llm_output, re.DOTALL)
    if match:
        try:
            return json.loads(match.group(0))
        except json.JSONDecodeError:
            pass

    # 策略 5：兜底 — 返回原始文本作为 reasoning，标记为解析失败
    return {
        "is_ad": None,
        "risk_level": "unknown",
        "parse_error": True,
        "raw_output": llm_output
    }
```

**此外，Prompt 中应该加一句强约束：**

```
"你必须只输出一行合法的 JSON，不要包含任何 markdown 标记、解释文字或换行。"
```

但这仍然不能 100% 保证。**多层解析 + 失败标记** 是必要的工程实践。

### 🟢 风险四：Embedding 模型下载 —— 已解决（你有梯子）

**决策：使用本地模型 `BAAI/bge-m3`，通过 ChromaDB 内置支持加载。**

你有梯子，HuggingFace 下载不是问题。具体流程：

```python
# ChromaDB 内置支持 sentence-transformers，两行代码加载 BGE-M3
from chromadb.utils import embedding_functions

embed_fn = embedding_functions.SentenceTransformerEmbeddingFunction(
    model_name="BAAI/bge-m3"  # 首次自动从 HuggingFace 下载，约 2GB
)
```

**注意事项**：
- 首次运行时 ChromaDB 会自动从 HuggingFace 下载模型（~2GB），**开着梯子等它下完**
- 下载后缓存到 `~/.cache/huggingface/hub/`，之后启动**无需网络、无需梯子**
- BGE-M3 是中文 Embedding 目前最好的开源模型之一，1024 维向量
- 论文可写"采用本地 Embedding 方案，避免了云端 API 的网络延迟、调用费用与数据传输隐私风险"

#### 费用估算（做实验需要多少钱）

```

  Input: ~2000 tokens (Prompt + 检索结果)
  Output: ~500 tokens (JSON 结果)
  费用: 2000/1000 × $0.0025 + 500/1000 × $0.01 ≈ $0.01 = 约 7 分人民币

单次 LLM 调用估算（DeepSeek）：
  Input: ~2000 tokens
  Output: ~500 tokens
  费用: 2000/1000 × ¥0.001 + 500/1000 × ¥0.002 ≈ ¥0.003 = 约 0.3 分人民币

实验总费用估算：
  200 条测试 × 4 组实验 = 800 次调用
  用 GPT-4o: 800 × ¥0.07 ≈ ¥56
  用 DeepSeek: 800 × ¥0.003 ≈ ¥2.4

  加上开发阶段的反复测试（假设 500 次）：
  用 GPT-4o: 500 × ¥0.07 ≈ ¥35
  用 DeepSeek: 500 × ¥0.003 ≈ ¥1.5

  总计（含 Embedding 费用）：
  DeepSeek 方案：< ¥20 人民币
  GPT-4o 方案：< ¥150 人民币

### 🟡 风险六：提示工程效果不确定 —— 实验数据可能不好看

#### 风险描述

提示工程是"玄学"——同样的 Prompt，不同模型表现差异很大，同一模型不同温度参数也差异很大。可能出现：

- **基线不准**：裸 LLM 本身就有 80%+ 准确率，加了 RAG 只提升到 82%，差异不显著
- **甚至倒退**：加了 RAG 检索到的一些不相关内容反而干扰了 LLM 判断，准确率下降
- **指标平平**：F1 只有 0.7 左右，论文写起来不好看

#### 应对策略

1. **先跑通再优化**：不要一开始就追求高指标，先让流程跑通
2. **选好测试集**：测试集里包含一些"仅靠常识无法判断，必须引用法规才能判对"的案例，这样 RAG 组的优势才能体现
3. **保留原始数据**：即使结果不理想，也要诚实地呈现在论文中。**对于本科毕设，实验设计的严谨性 > 指标的高低。** 失败的分析（"为什么加了 RAG 反而下降"）有时候比成功的分析更有学术价值
4. **即使数据不够好，论文也有的写**：
   - 分析为什么 RAG 在某些情况下效果不好（检索噪声、相似度阈值不当）
   - 分析为什么提示工程有天花板（模型本身对"隐性广告"概念的理解局限）
   - 讨论如何改进（更好的检索策略、更细粒度的知识库分类）

### 🟡 风险七：ChromaDB 版本兼容性

#### 风险描述

ChromaDB 也在快速迭代中。0.4.x → 0.5.x 之间有 API 变化。如果你照着网上教程写代码，很可能因为版本不匹配而报错。

#### 解决方案

```bash
# 固定版本安装（非常重要！）
pip install chromadb==0.5.5

# 然后对着 0.5.x 的官方文档写代码
# https://docs.trychroma.com/docs/overview/introduction
```

在你的 `requirements.txt` 中**锁定所有版本号**：

```
chromadb==0.5.5
openai==1.55.0
fastapi==0.115.0
uvicorn==0.30.0
streamlit==1.40.0
pandas==2.2.0
scikit-learn==1.5.0
pydantic==2.9.0
```

**为什么要锁定版本？** 因为你几个月后写论文时如果重新 pip install，可能新版 API 已经变了，代码跑不起来，你又得 debug。

### 🟡 风险八：测试集标注质量

#### 风险描述

你需要 100-200 条人工标注的测试数据。但：
- 你自己标注，标准一致吗？
- 你对广告法的理解够准确吗？
- 标注了 100 条后发现前面 20 条标准不一致怎么办？

#### 解决方案

1. **先制定标注规范**（写一个简短的标注指南）
2. **分批次标注**：每标 30 条回顾一次，校准标准
3. **用 LLM 辅助标注**：让 LLM 先标一遍，你再复核/修正（快很多）
4. **标注指南示例**：

```
标注标准（简版）：
1. 是否提及具体品牌/产品/服务名称？ 是 → 继续判断
2. 是否存在购买引导/推荐语气？ 是 → 继续判断
3. 是否标注了"广告""合作"等标识？ 否 → 隐性广告嫌疑
4. 内容描述是否客观属实？ 否 + 夸大 → 高风险

标签：
- is_ad: 是/否
- ad_type: 种草/软文/测评伪装/经验伪装/品牌露出/其他
- risk_level: 高/中/低/无
```

在与导师沟通前，你需要对以下问题有明确答案：

  └── 写一个 test_rag.py，用 5 条真实法规 + 1 条测试文本
  └── 产出：核心链路跑通（这是最重要的里程碑！）

## 六、最后的实话
